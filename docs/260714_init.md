# Initial design notes

The implementation uses OpenCode's generic `event` hook and filters for `session.created`. OpenCode does not await
event hooks, so the handler immediately records the startup promise for every new root, forked, child, or subagent
session. A synchronous activation-local guard marks the session ID before asynchronous startup begins.

OpenCode does await `chat.message` before saving the original user message. The matching session's first message awaits
that recorded promise. If an existing or resumed session did not emit `session.created` in the current plugin/directory
instance, its first message creates and awaits the startup promise instead. The same session ID cannot start twice in
one activation, while different IDs run independently. When `injectOutput` is enabled, the plugin appends one synthetic
text part to the message that consumes the startup result; it never calls `client.session.prompt` and therefore never
creates a separate user message or model turn. Later messages neither rerun startup nor receive another synthetic part.

Configuration is supplied through the supported plugin tuple shown in the README. The command is intentionally fixed:
if `<exact session directory>/package.json` contains a string `scripts["dev:start"]`, the plugin runs
`bun run dev:start` in that directory. For an existing session first seen through `chat.message`, the plugin input
directory is used because that hook does not include a session directory.

Merely viewing or loading an existing session emits neither hook, so an OpenCode server plugin cannot detect that
passive action. Switching away and back within one backend instance does not rerun startup. Restarting the plugin
instance or backend clears its in-memory state, after which the first message to an existing session runs startup again.
Separate OpenCode processes have independent state.

`dev:start` must launch or signal an independently managed service and terminate. A foreground process would keep the
first prompt waiting. Logging is detached and best-effort; command and logging failures remain nonfatal.
